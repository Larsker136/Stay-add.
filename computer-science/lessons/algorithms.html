7.1Algorithm design

Analyse, design, code, test

Programs aren’t written by typing straight away. First understand the problem, then design a solution, then code it, then test it — and go back round whenever something doesn’t work.

1

Understand

Two sections and a checklist

7.1.1

The program development life cycle

StageWhat happens
Analysisidentify the problem and the requirements; use abstraction and decomposition
Designplan the solution: structure diagrams, flowcharts, pseudocode
Codingwrite the program in a programming language; test each module as it is written (iterative testing)
Testingrun the complete program with test data to check it meets the requirements and has no errors
7.1.2

Abstraction and decomposition

  • abstraction: removing unnecessary details and keeping only what is needed to solve the problem — a map of a train network shows the stations and lines, not every building
  • decomposition: breaking a complex problem down into smaller, more manageable parts, each of which can be solved separately
  • every system can be described as its inputs, processes, outputs and storage

Exam tip. Know which stage each activity belongs to: “identifying requirements” is analysis; “writing pseudocode” is design.

7.2Algorithm design

Big systems are made of small ones

A computer system is built from sub-systems, which are built from smaller sub-systems. A structure diagram shows that breakdown at a glance.

1

Understand

Two sections and a checklist

7.2.1

Systems and sub-systems

  • every computer system is made up of sub-systems, which may themselves be made of further sub-systems
  • decomposing a problem into sub-systems means each part can be designed, coded and tested separately — and by different people
  • a sub-system can be described by its inputs, processes, outputs and storage
7.2.2

Structure diagrams

A structure diagram shows the hierarchy of a system: the whole system at the top, broken down level by level into smaller sub-systems.

2

Interpret

Chains to remember, then check yourself

Exam tip. In a structure diagram, the top box is the whole system and lines only connect a box to the boxes directly below it.

7.3Algorithm design

Pseudocode, flowcharts and trace tables

An algorithm is a precise set of steps. Write it as pseudocode or draw it as a flowchart, then check it by tracing it by hand, one line at a time.

1

Understand

Three sections and a checklist

7.3.1

Pseudocode

Pseudocode describes an algorithm in structured English-like statements. Cambridge style:

// sequence, assignment, input and output
INPUT Mark
Total ← Total + Mark
OUTPUT "Total is ", Total
// selection
IF Mark >= 50 THEN
   OUTPUT "Pass"
ELSE
   OUTPUT "Fail"
ENDIF
// iteration
FOR Count ← 1 TO 10 … NEXT Count
WHILE Mark < 0 DO … ENDWHILE
REPEAT … UNTIL Mark >= 0
7.3.2

Flowcharts

SymbolShapeMeaning
Terminatorrounded rectangleSTART or STOP
Processrectanglea calculation or assignment, e.g. Total ← Total + Mark
Input / outputparallelogramINPUT or OUTPUT
Decisiondiamonda question with Yes / No branches
Subroutinerectangle with double sidesa call to a procedure or function
Flow linearrowthe order of the steps
7.3.3

Trace tables

  • a trace table has a column for each variable (and the output) and records their values as the algorithm is dry-run by hand
  • it is used to find what an algorithm does, to check its output for given test data, and to find logic errors
  • when asked the purpose of an algorithm, trace it with sample data and describe what the output means

7.4Algorithm design

Search, sort, total, count

A few patterns turn up in almost every program: looking for an item, putting a list in order, adding things up, counting them, and finding the biggest, smallest and average.

1

Understand

Four sections and a checklist

7.4.1

Linear search

Check each item in turn, from the first, until the target is found or the list ends.

Found ← FALSE
Index ← 1
WHILE Found = FALSE AND Index <= 10 DO
   IF List[Index] = Target THEN
      Found ← TRUE
   ELSE
      Index ← Index + 1
   ENDIF
ENDWHILE
7.4.2

Bubble sort

  • compare each pair of neighbouring items; swap them if they are in the wrong order
  • after one pass the largest item is at the end; repeat for the remaining items
  • a Swap flag records whether any swaps were made in a pass; if none, the list is sorted and the algorithm stops early
7.4.3

Totalling and counting

Total ← 0
Count ← 0
FOR Index ← 1 TO 30
   Total ← Total + Mark[Index]       // totalling
   IF Mark[Index] >= 50 THEN
      Count ← Count + 1              // counting
   ENDIF
NEXT Index

Always initialise totals and counters (to 0) before the loop.

7.4.4

Maximum, minimum and average

Max ← Mark[1]
Min ← Mark[1]
FOR Index ← 2 TO 30
   IF Mark[Index] > Max THEN Max ← Mark[Index] ENDIF
   IF Mark[Index] < Min THEN Min ← Mark[Index] ENDIF
NEXT Index
Average ← Total / 30

Start Max and Min from the first item (or from a value lower / higher than any possible item).

7.5Algorithm design

Reasonable data, entered accurately

Validation checks that data makes sense before it is accepted. Verification checks it was entered correctly. Test data checks that the program itself behaves.

1

Understand

Three sections and a checklist

7.5.1

Validation checks

CheckWhat it testsExample
Range checkvalue is between a lower and upper limitage 11–18
Length checknumber of characters is exact or within limitspassword at least 8 characters
Type checkdata is the right data typeage is an integer
Presence checkdata has been enteredname is not left blank
Format checkdata follows a set patternstudent ID like AB1234; date DD/MM/YYYY
Check digitfinal digit recalculated from the othersISBN, barcode
REPEAT
   INPUT Age
   IF Age < 11 OR Age > 18 THEN OUTPUT "Age must be 11 to 18" ENDIF
UNTIL Age >= 11 AND Age <= 18
7.5.2

Verification checks

  • double entry: data is entered twice and the two copies are compared (e.g. a new password)
  • visual check: the user looks over the data on screen and confirms it matches the original

Neither proves it is correct Validation only shows data is reasonable; verification only shows it was entered as intended. A wrong but sensible value can pass both.

7.5.3

Test data

TypeMeaningFor “age 11–18”
Normaldata that should be accepted14
Abnormal (erroneous)data that should be rejected30, −2, “twelve”
Extremethe largest and smallest values that should be accepted11 and 18
Boundaryvalues at each limit and just beyond it — one accepted, one rejected10 and 11; 18 and 19

7.6Algorithm design

Find the bug, fix the line

Some errors stop a program running; others let it run and quietly give the wrong answer. Tracing with test data shows exactly where it goes wrong.

1

Understand

Two sections and a checklist

7.6.1

Types of error

ErrorWhat it isExample
Syntax errorbreaks the rules of the language; the program will not translateIF X > 3 THN, a missing ENDIF
Logic errorthe program runs but gives the wrong resultusing > instead of >=; wrong loop limit; total not initialised
Run-time errorthe program crashes while runningdividing by zero; reading past the end of an array
7.6.2

Finding and correcting errors in algorithms

  1. read what the algorithm is supposed to do
  2. choose test data and work out the expected output
  3. trace the algorithm with that data, using a trace table
  4. where the trace differs from what you expected, find the line responsible
  5. write the corrected line; then trace again to check

Common culprits: variables not initialised, loops running one time too many or too few, the wrong comparison operator, totals overwritten instead of added to.
